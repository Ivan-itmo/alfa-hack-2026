# Scoring Engine — прозрачный конвейер оценки кредитного риска

Python-микросервис (FastAPI), который превращает оценку риска из «чёрного ящика»
в объяснимый конвейер с **небинарными исходами** и текстовым объяснением от LLM.

## Что делает

1. Считает долговую нагрузку **DSTI** и прозрачный **скоринг-балл** (0–1000).
2. Принимает одно из **5 решений** (не «одобрено/отказано»).
3. Для встречного предложения **автоматически подбирает** безопасные сумму/срок.
4. Просит локальную LLM объяснить решение **простым русским языком**.
5. Всегда возвращает список `key_factors` — почему решение такое.

# В составе всего стека

## Контракт API

### `POST /api/v1/scoring/evaluate`

**Вход:**

```json
{
  "company_inn": "7701000002",
  "monthly_revenue": 1500000,
  "monthly_net_profit": 350000,
  "company_age_months": 18,
  "requested_amount": 3000000,
  "requested_term_months": 12,
  "product_rate": 0.165,
  "bki_active_loans_monthly_payment": 60000,
  "bki_delinquency_days": 0,
  "has_bankruptcy": false
}
```

**Выход:**

```json
{
  "decision": "COUNTER_OFFER",
  "score_value": 610,
  "dsti": 0.51,
  "offer": {
    "amount": 1600000,
    "term_months": 18,
    "monthly_payment": 101000,
    "interest_rate": 0.165
  },
  "required_documents": [],
  "key_factors": [
    {"factor": "DSTI", "impact": "negative", "description": "Высокая долговая нагрузка"},
    {"factor": "AGE", "impact": "positive", "description": "Бизнес работает более года"}
  ],
  "ai_explanation": "Мы не можем выдать 3 000 000 ₽, чтобы не перегружать бюджет…",
  "approved_amount": 1600000,
  "approved_term_months": 18,
  "monthly_payment": 101000,
  "interest_rate": 0.165,
  "rejection_reason": ""
}
```

> **Про совместимость.** В ответе есть и вложенный `offer`, и плоские поля
> (`approved_amount`, `approved_term_months`, `monthly_payment`, `interest_rate`,
> `rejection_reason`). Плоские поля нужны, чтобы существующий Go-клиент
> (`internal/scoring/client.go`) принял ответ без изменений: его валидация
> ждёт именно плоскую структуру. Так контракт из задания и текущий бэкенд
> сосуществуют одновременно.

## Формулы

**DSTI** (долговая нагрузка):

```
DSTI = (Платежи в БКИ + Новый ежемесячный платёж) / Среднемесячная чистая прибыль
```

**Аннуитетный платёж** (ставка в годовых процентах, как в Go: `rate/1200`):

```
PMT = S · r / (1 − (1+r)^(−n)),   r = rate/1200
```

**Предельный платёж для встречного предложения:**

```
PMT_max = Чистая прибыль × 0.35 − Платежи в БКИ
```

## Логика 5 исходов

Порядок проверок намеренно детерминирован и прозрачен:

| # | Условие | Решение |
|---|---------|---------|
| 1 | Банкротство ФНС, или просрочка > 90 дней, или прибыль ≤ 0 | **REJECTED** |
| 2 | Возраст < 6 мес. **и** нет кредитной истории **и** документы не приложены | **DOCS_REQUIRED** |
| 3 | DSTI > 0.55 | **REJECTED** (нагрузка непосильна) |
| 4 | Скоринг-балл в зоне 450…550 | **MANUAL_REVIEW** (ручной разбор) |
| 5 | DSTI ≤ 0.35 | **APPROVED** (запрошенные условия) |
| 6 | 0.35 < DSTI ≤ 0.55 | **COUNTER_OFFER** (безопасные условия) |

### Как строится встречное предложение

1. **Сначала пробуем сохранить сумму**, увеличивая срок (в пределах 1–60 мес.),
   пока платёж не уложится в `PMT_max`.
2. **Если срок не спасает — снижаем сумму** (округление вниз до 50 000 ₽).

Так клиент по возможности получает запрошенную сумму, но с комфортным платежом.

## Объяснение через LLM (Explainable AI)

`scoring_service/llm.py` передаёт решение в локальную OpenAI-совместимую LLM.

**Критично для модели `gemma4:12b`:** по умолчанию она пишет ответ в
`reasoning_content`, а `content` оставляет пустым и обрывается по лимиту токенов
(3–5 секунд). Поэтому запрос отправляется с флагом:

```json
"chat_template_kwargs": {"enable_thinking": false}
```

После этого модель отдаёт готовый `content` за **0.8–1.6 секунды** — укладываемся
в требование ≤ 2 сек.

**Надёжность:** если LLM недоступна или отвечает дольше таймаута, слой объяснений
переключается на детерминированный шаблон (`_template`), поэтому `ai_explanation`
**никогда не бывает пустым** — демо не сломается.

## Настройка (переменные окружения)

| Переменная | По умолчанию | Смысл |
|-----------|--------------|-------|
| `DSTI_APPROVE_MAX` | `0.35` | Верхняя граница DSTI для одобрения |
| `DSTI_COUNTER_MAX` | `0.55` | Верхняя граница DSTI для встречного |
| `SAFE_PAYMENT_RATIO` | `0.35` | Доля прибыли под новый платёж |
| `DELINQUENCY_STOP_DAYS` | `90` | Порог просрочки-стоп-фактора |
| `YOUNG_BUSINESS_MONTHS` | `6` | Порог «молодого» бизнеса |
| `SCORE_MANUAL_REVIEW_LOW/HIGH` | `450`/`550` | Зона ручного разбора |
| `AI_BASE_URL`, `AI_MODEL`, `AI_TIMEOUT` | из общего `.env` | Доступ к LLM |

## Замечание о примере из задания

В задании для входа `3 000 000 ₽ / 12 мес.` при прибыли `350 000 ₽` указан
`DSTI = 0.51`, но по формуле выходит **0.95** (платёж ≈ 272 900 ₽).

Проверка: предложение из задания `1 600 000 ₽ / 18 мес.` при 16.5% даёт платёж
**100 949 ₽** — ровно их же «≈ 101 000 ₽». То есть финансовая математика в примере
верна, а вот сам DSTI во входе посчитан неверно.

Наш сервис следует **формулам и порогам из ТЗ**, а не арифметике примера:
для приведённого входа он честно вернёт `REJECTED` (DSTI 0.95 > 0.55).
Ветка `COUNTER_OFFER` проверяется в тестах и на примерах из `tests/`.
